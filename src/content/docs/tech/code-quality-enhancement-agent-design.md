## 一、定位（一句话）

**平台做 MCP 任务中枢，开发者的会话 agent 做执行体**：平台发现/分发/验证质量问题 → 开发者 agent 拉任务修复 → push 后平台自动验证闭环。人只在两个位置出现：开发者确认修复（逐条）、张亮评审高风险与裁定误报。

## 二、架构总图

```
┌─────────────── 平台（ai_code_scan）───────────────┐
│ 发现：引擎 v1（现役）/ v2（规划中，SARIF 统一）      │
│ 分发：MCP server ── 三工具最小集                    │
│   get_task（拉任务包：问题+上下文+规则版本）          │
│   report_result（回写：已修复/误报标记）             │
│   query_rules（查规则/红线/版本）                   │
│ 验证：复用 push webhook → 增量审查 → 指纹消失=闭环   │
│ 计量：token 走平台模型代理，llm_usage 统一核算       │
└──────────────────────┬───────────────────────────┘
                       │ MCP（任务队列模式）
┌──────────────────────┴───────────────────────────┐
│ 开发者侧：code-quality-agent 技能（人人可装）        │
│   拉任务 → 三档修复权纪律执行 → 过 push-gate 门禁    │
│   → push →（平台自动验证）→ 汇报                    │
│ 降级：平台不可用时机械级检查本地跑，语义级明示拒绝     │
└──────────────────────────────────────────────────┘
```

## 三、17 项决策记录（三轮盘问全档）

### 第 1 轮 · 核心使用场景
| # | 决策 |
|---|------|
| Q1 | 团队人人有会话环境，agent 面向全员；**平台提供 MCP 服务/推送**（批注方向，第 2 轮落实） |
| Q2 | 交付物 = 推送→修→验（第 2 轮 R2-3 补定） |
| Q3 | 修复权严格逐条确认（信任保守；主体第 2 轮 R2-5 移交开发者） |
| Q4 | 门禁关系 = 机械级门禁永在（终审），agent 是预检+修复教练 |
| Q5 | 存量治理 = 触碰式为主 + 项目制为辅 |
| Q6 | 平台依赖 = 混合降级（机械级本地、语义级强依赖） |

### 第 2 轮 · 执行体与推送架构
| # | 决策 |
|---|------|
| R2-1 | **团队都有 agent 环境**（推送地基成立） |
| R2-2 | 推送通道 = **MCP 终态**（不做邮件过渡） |
| R2-3 | 交付物 = 平台推问题包→开发者修→平台验证（责任归代码归属者） |
| R2-4 | 张亮角色 = 阈值混合（低风险自动推、高风险经评审） |
| R2-5 | 逐条确认主体 = 开发者；张亮保留平台验证权+抽查权 |
| R2-6 | 存量启动 = 试点仓验证先行 |

### 第 3 轮 · 落地形态
| # | 决策 |
|---|------|
| R3-1 | 试点仓 = 自家仓 G20_soft_platform/aidevops（狗粮） |
| R3-2 | MCP 工具面 = 三工具最小集（get_task / report_result / query_rules）；graph_query 等引擎 v2 落地后再开 |
| R3-3 | 验证触发 = 复用 push webhook 增量审查链路（零新代码，指纹消失=闭环） |
| R3-4 | 误报回流 = 开发者标记→候选池→张亮批量裁定→规则库调优 |
| R3-5 | token 成本 = 平台统一出（llm_usage 计量），开发者会话 token 自理 |
| R3-6 | 开发者侧 = 统一技能包装（code-quality-agent 技能固化三档修复权纪律） |

## 四、关键事实（已注入设计）

- 存量未解决问题 **27,716** 条，**91%（25,342）位于高频分支**（被审查≥3次）→ 触碰式治理随变更自然消化九成，无需专项运动；剩 9% 在死分支（随分支淘汰/项目制点杀）
- 平台已有可复用件：push webhook 增量审查（验证闭环）、push-gate 三层门禁（L1/L2）、llm_usage 计量、agent token 鉴权机制、规则版本化（prompt_git）

## 五、分期计划

| 期 | 内容 | 验收 |
|----|------|------|
| **P0 试点闭环** | MCP server 三工具 + 任务队列（issues 派生）+ 开发者技能 v1 + 自家仓真跑：拉任务→修→push→指纹消失 | 试点仓 ≥1 个真实问题全闭环；修复率与误报率数据落地 |
| P1 全员推广 | 技能分发 + 阈值评审界面（你的低/高风险分流）+ 误报裁定工作台 | ≥2 个业务仓接入，周报自动化 |
| P2 能力增强 | 引擎 v2 落地后 MCP 加 graph_query/baseline；误报阈值自动降级；规则库调优半自动化 | token 降比与召回对比数据 |

## 六、边界与非目标

- 平台 agent 不代改任何人的仓（权限与信任边界，R2-3 否决）
- 门禁终审权永在机械层（Q4：agent 不当自己的裁判）
- 页面冻结新功能+抽公共层（前置决策不变）；mq-page 保留服务会话外异步问卷场景

## 七、盘问工具沉淀（本次副产物）

- **会话内**：DSH 原生问答组件（本轮 R2/R3 实证体验最佳，零跳转）
- **会话外**：平台 `/mq-page` + 3 API（建轮/提交/拉取，agent token 鉴权，E2E 已过）——团队摸底、跨会话异步收集用
- 双轨选择准则：**答题人在 DSH 会话里→原生；不在→链接页**
