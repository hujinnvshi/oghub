## 一、这个系统到底是干什么的

**一句话**：开发者提交代码（push 或提 MR）时，平台自动用大模型审查这批改动，把问题记下来，在网页上展示给人看，同时（可选）邮件通知；另外支持手动对整个仓库做一次"全量扫描"。

**它不做什么**：不改代码、不做测试、不部署、不替代 GitLab。

## 四、一条主线的数据流（跟着一段代码走一遍）

```
① 你在 GitLab push 一个文件
② GitLab 的 hook 把「这次改动」发给平台 /push-check
③ 平台拉取：规则（红线条款）+ 提示词 + 模型 → 调大模型审查
④ 模型返回 JSON：问题清单（文件/行号/等级/描述/建议）
⑤ 平台写库：reviews（这次审查）+ issues（每条问题，带指纹去重）
⑥ 页面展示：问题列表可看、可标忽略/已解决
⑦ （可选）发邮件给配置的收件人
⑧ 你下次 push 同一位置没再出现 → 该问题标记为"已消失"
```

**关键点**：同一类问题不会重复堆积，靠「指纹」——文件+位置+类型的组合做唯一标识。

## 五、四个容易忘的机制（为什么这么设计）

**1. 为什么有两台服务器跑同一套平台？**
外网 GitLab 和外网 GitLab 互相看不见（网络隔离），所以外网服务只服务外网 GitLab，内网服务只服务内网 GitLab。**数据库只有一份**（放在外网 <审查服务主机>），内网服务跨网写这一份库——所以两台看到的页面数据是同一份。

**2. 为什么 hook 里会拦住 push？**
hook 是 GitLab 侧的小脚本，push 时先跑它：检查提交信息规范（`type(scope): subject`）、扫密钥（gitleaks）、有问题就拒绝这次 push。**它是唯一能真正"阻止"问题进仓的关卡**，平台页面只能事后展示。

**3. 为什么规则能在页面上改、还能回滚？**
红线条款和审查提示词存在数据库里（当前生效值）+ 本地 git 仓库里（历史版本）。每次保存 = git 提交一次 → 所以能看 diff、能回滚任意历史版本。改这些需要手机动态码（MFA），防止误改。

**4. 为什么备份要盯两台机器？**
两台 GitLab 的数据各在各的机器上，各自备份到各自的"另一台机器"：外网备份到 <外网备份服务器>，内网备份到 <内网备份服务器>。**内网这条链路今年断过 7 个月**，9-30 修好过一份，目前每周六自动跑（还有小尾巴：自动任务偶尔传不完，待观察）。

## 六、坏了怎么办（运维速查）

| 症状 | 先查 | 处理 |
|------|------|------|
| 页面打不开 | `curl <审查服务主机>:8081/health` | 不通 → 主机可能宕机（有过一次，需机房上电）；通了但页面 500 → 看 `logs/code_scan.log` |
| 服务重启无效 | `ps aux \| grep ai_code_scan` | 可能有人手动 nohup 起过进程占着 8081（踩过）→ 杀掉后用 systemctl restart |
| push 被拦 | 看 hook 输出提示 | 提交信息不规范/有密钥；改完重提 |
| 问题列表没数据 | 看该仓库是否在配置面板纳管 | 未纳管 → 配置面板加产品/项目/仓库/分支 |
| 审查结果不生效 | 规则是不是刚改过 | 全量扫描按"发起时快照"，push/MR 实时读，最多差 1 分钟 |
| 内网服务没起 | 内网机计划任务 AICodeScan | 状态"运行中"但没进程 = 僵死 → schtasks /end 再 /run |
| 备份没传到异地 | 看 `/var/log/localbackup/backup_upload.log` | 已知问题：连接会周期性断，靠断点续传 |
